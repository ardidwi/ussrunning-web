# BE-16 Application Notification Service

## Architecture and boundaries
Domain mutation -> invoker outbox trigger -> durable notification_deliveries intent -> typed code-owned template -> existing EmailProvider -> sanitized delivery persistence. No new infrastructure/provider/package. Registration/pass services, account/Auth provider and permanent identities are unchanged. BE-03 verification still owns single-use proofs and its synchronous proof-in-memory delivery; schema_version=0 rows are excluded from generic dispatch/retry. Neon Better Auth OTP/password mail is completely separate.

## Model / migration 017
Reuses uss.notification_deliveries, retaining every legacy field/row and status constraint. Adds schema_version, template_key/version, typed payload snapshot, pass_id, next_attempt_at, retryable, cancelled_at, claimed_at, first_attempt_at, claim_id, envelope_hash, updated_at/version. UUID identity, existing unique idempotency key and provider message index reused. Composite pass/registration/event FK prevents cross-event association. A partial due index supports future bounded workers. Identity/template/recipient/payload are immutable; physical delete/truncate rejected. No new table, persistent migration, historical backfill or automatic email send.

Application DTO maps queued to pending and cancelled_at to cancelled; operational lifecycle pending -> sending -> sent/failed, or retained cancelled. Legacy delivered/bounced values remain supported only for older rows; BE-16 never fabricates receipts. Sent means provider acceptance, not inbox delivery.

## Implemented types and integrations
Code-owned v1 templates: registration_confirmed, registration_waitlisted, registration_cancelled, event_pass_available. AFTER INSERT/status-transition registration hook captures only authoritative confirmed/waitlisted/cancelled outcomes. Unchanged duplicate action creates nothing. A new cancellation/re-registration cycle has its own occurrence key. AFTER INSERT of an active BE-09 format-v1 pass captures availability once per immutable pass ID. No pass token/hash or permanent barcode is stored in notification payload/email. The dashboard link is the credential-free access path.

Pending superseded registration/pass availability intents are retained as cancelled. Dispatch rechecks active/verified account, exact recipient snapshot, current registration status, event access/lifecycle and pass eligibility. Historical migration rows are never automatically mailed. Revoke-specific and check-in emails are deferred: no useful approved consumer warrants additional noisy operational email. Existing account verification remains available through BE-03; no new generic auth/admin arbitrary email type is invented.

## Templates / recipient / consent
Recipient is resolved by SQL from the authoritative account, never browser input. Immutable payload contains trusted event title/slug, date/time/timezone, registration ID/status, optional name/venue/instructions snapshots. Optional member name is the minimum personalization needed by PRD; no phone, birth date, emergency contact, role/auth data or body/token duplication. Snapshot stability is required for provider replay with identical content. Operational messages are not marketing: existing marketing opt-in is neither silently changed nor repurposed as an auth/event-delivery gate. Marketing/bulk and preference UI remain out of scope.

Validation rejects unknown fields, markup/scripts/control characters, oversized text, bad UUID/date/timezone/slug, arbitrary template key/version and recipient. Optional name160, venue500, instructions1200; event title400, payload4KiB. HTML escapes every dynamic string; text fallback included. APP_BASE_URL must be a canonical HTTPS origin (development HTTP loopback only), no credentials/path/query/fragment. Dashboard registration and public event detail paths are server-constructed; members-only events link to the owner dashboard instead, no client callbacks/redirects. No public unrestricted send/upload endpoints.

## Idempotency / atomicity / retry
Domain row and intent commit or rollback together. Outbox capture failure rolls back the transaction rather than silently lose the event; provider/config/network failure never rolls back a committed registration/pass. No external network call occurs under the domain/claim locks. Trigger keys are registration UUID + status + authoritative transition timestamp; pass key is pass UUID + available/v1. Existing UNIQUE(idempotency_key) is final protection.

Invoker claim orders account locks by UUID, locks trusted actor roles, then event/registration/pass and delivery. It rechecks events.manage-equivalent DB role/lifecycle after locking, expectedVersion, eligibility, retry time and claim state. Concurrent duplicate claims cannot both send. Claimed attempt has a UUID fence; finish requires that fence and sending status. Managed retry audit is atomic with the claim; audit failure prevents send. Managed cancellation + audit is atomic.

Safety policy v1: maximum3 attempts, backoff60 then300 seconds, stale sending lease5 minutes, replay horizon20 hours from first attempt. No automatic retry timer/worker/cron exists. Authorized explicit dispatch can recover stale sending after lease; same key/provider/envelope hash must be reused. A DB failure after acceptance may leave sending; recovery never creates a new key. Changing sender, canonical origin, template/rendered content or provider conflicts with existing envelope. Operator must reconcile expired/uncertain rows; never reset attempt count/key or replay after horizon.

Resend retains matching-payload idempotency for24 hours; our shorter20-hour horizon leaves safety margin ([official idempotency contract](https://resend.com/changelog/idempotency-keys)). Retries fail closed unless the adapter explicitly declares idempotencyRetentionSeconds >=72000. Any future provider must honor this declared replay/idempotency contract; Resend declares86400. At-most-one provider acceptance is conditional on provider idempotency; PostgreSQL alone cannot prove exactly-once external delivery. Late in-flight acceptance cannot be unsent after subsequent cancellation/account restriction; links always reauthorize and emails are not entitlement.

## Provider / configuration
Reuse EmailProvider, EmailContent and pinned Resend6.13.0. Shared getTransactionalEmailConfig lazily validates existing RESEND_API_KEY, EMAIL_FROM_ADDRESS, EMAIL_FROM_NAME, APP_BASE_URL and EMAIL_PROVIDER_TIMEOUT_MS. Existing getEmailConfig composes transport with unchanged verification-only policy. No new env names, provider rotation or eager build/public-page failure.

Adapter adds optional retryable classification while preserving existing result codes for BE-03. Network/timeout, provider rate/server/concurrent-idempotent failures retry conservatively; validation/auth/domain/unknown rejections are permanent. Only normalized fixed codes reach DB/actions; no arbitrary provider exception/body/header/key logs. Missing config leaves intent pending and returns NOTIFICATION_PROVIDER_UNAVAILABLE, never fake sent. Sending domain/DNS must be verified separately. HTML/text code-owned, notification_templates CMS editing not enabled.

## Managed contracts / authorization
lib/notifications/notification-actions.ts: listManagedNotifications({type?,status?,limit?,cursor?}), getManagedNotification({id,expectedVersion}), dispatchManagedNotification({id,expectedVersion}), cancelManagedNotification({id,expectedVersion}). Existing events.manage; active/verified admin or super_admin, fresh server authorization + DB recheck. No new role/permission, arbitrary recipient or client provider injection. Member/anonymous/restricted account access rejected. Verification deliveries cannot be inspected/retried through this operational service.

DTO: id,type,channel,status,eventId,registrationId,passId,attemptCount,retryable,nextAttemptAt,queuedAt,sentAt,failedAt,version,errorCode,provider. Omits recipient/account ID, private payload/body, idempotency/envelope/claim secrets and raw token/hash. List default20/max50, queued_at DESC/id ASC cursor with status/type binding. No unbounded/bulk send operation. Dispatch returns a processed attempt result with code NOTIFICATION_SENT or NOTIFICATION_SEND_FAILED and safe status DTO; callers must not interpret processed intent as inbox delivery. Validation/permission/conflict/config failures return ok:false stable codes.

Errors: NOTIFICATION_NOT_FOUND, FORBIDDEN, INVALID_RECIPIENT, INVALID_TEMPLATE, PROVIDER_UNAVAILABLE, SEND_FAILED, ALREADY_SENT, CONFLICT, RATE_LIMITED, NOT_RETRYABLE, UNAVAILABLE (NOTIFICATION_ prefix). Existing account lifecycle codes retained. Invalid pre-send content returns controlled validation error and remains unsent for operator inspection; immutable intent is not silently rewritten.

## Audit / operations / staging
Managed retry_requested and cancelled audits contain actor/notification ID, attempt count or changed-field names only. Routine provider transitions do not spam audit history. Existing audit immutability retained. Delivery contains necessary recipient/name PII; staging must define access/retention policy without deleting operational history casually.

No real email, persistent DB migration, verified sender/domain/credential change in this task. Tests use PGlite and provider fakes; independent Neon sessions and actual sender/client/inbox/timeout reconciliation remain staging gates. Rehearse017 + runtime grants on an isolated branch before deployment cutover. No startup migration. Roll forward with a new migration; rollback application code may leave additive columns/history intact. Do not replay old intents through pre-BE16 code.

Future: authorized automatic bounded worker/drain, webhook delivered/bounce tracking, owner notification UI/preferences for optional communications, broader BE-21 observability and admin operational UI. A worker must use trusted scoped service identity, not an unauthenticated HTTP endpoint. Real-user/real-email operation triggers the roadmap's stricter lifecycle gates.
